# Spec: gh#21 — Remove dead Python 3.10 exceptiongroup compatibility shim

Date: 2026-10-13
Stage: review
Branch: `pipeline/gh-21`
Issue: https://github.com/puckdoug/zpdatafetch/issues/21

## Problem

The project's minimum supported Python is now 3.11 (Python 3.10 is
end-of-life). With that, the Python 3.10 compatibility shim in
`src/zpdatafetch/zpcyclistfetch.py:12-23` is dead code:

```python
# Python 3.10 compatibility
if sys.version_info >= (3, 11):
  from builtins import BaseExceptionGroup
else:
  # For Python 3.10, anyio provides ExceptionGroup
  try:
    from exceptiongroup import (  # ty: ignore[unresolved-import]
      BaseExceptionGroup,
    )
  except ImportError:
    # Fallback - catch the anyio exception type
    BaseExceptionGroup: type[BaseException] = Exception
```

`BaseExceptionGroup` is a builtin from 3.11, so the `else` branch, the
`exceptiongroup` backport import, and the `# ty: ignore[unresolved-import]`
suppression are all unnecessary. The `sys` import exists only to drive this
guard. Related stale artefacts:

- `src/shared/validation.py:204` carries a "Python 3.10 compatibility" comment
  and normalizes a trailing `Z` to `+00:00`; Python 3.11+
  `datetime.fromisoformat` accepts `Z` directly.
- `docs/planning/ty-exceptiongroup-unresolved-import.md` documents the ty
  suppression that this change removes.
- Stale comments in the `except BaseExceptionGroup` handler
  (`src/zpdatafetch/zpcyclistfetch.py:200-205`) describe the now-removed
  `Exception` fallback.

## Prerequisite / branch state

The issue premise (`requires-python = ">=3.11"`) reflects the maintainer's
in-progress "Python 3.11-3.15 support" change. That change is **not committed
on this branch**: `pyproject.toml` currently declares `requires-python =
">=3.10"` and `[tool.ty.environment] python-version = "3.10"`, and the CI
matrices still include `3.10`. See Assumptions — the version-configuration
change is owned by that separate support change, so this branch should be
rebased onto it before its CI is expected to pass on 3.10-less interpreters.

Removing the shim unconditionally is only valid once the project no longer
advertises 3.10 support. Nothing here requires 3.10 to remain importable.

## Required behavior

1. `src/zpdatafetch/zpcyclistfetch.py`:
   - Delete the `if sys.version_info >= (3, 11):` / `else:` block
     (lines 12-23) and replace it with a single unconditional
     `from builtins import BaseExceptionGroup`.
   - Remove the now-unused `import sys` (line 5).
   - In the `except BaseExceptionGroup as eg:` handler, the defensive
     `hasattr`/`callable` guard and the comments about the `Exception`
     fallback are obsolete. Use `eg.exceptions` directly: iterate the group,
     re-raise the first `NetworkError` with its existing message; if none is
     found, re-raise the group (`raise`). The old guard was always false
     (`ExceptionGroup` is not iterable), so a `NetworkError` from a child task
     was never surfaced; this corrects that latent bug. Exception messages are
     unchanged.
2. `src/shared/validation.py`:
   - Remove the stale "Python 3.10 compatibility" comment and the
     `value.replace('Z', '+00:00') if value.endswith('Z') else value`
     normalization, parsing directly with `datetime.fromisoformat(value)`.
     `parse_datetime_to_epoch` must still accept a trailing `Z` and return the
     same epoch values.
3. `docs/planning/ty-exceptiongroup-unresolved-import.md`: if present on the
   branch, mark it resolved/obsolete or remove it (it documents the
   suppression that no longer exists). If it is not present, nothing to do.
   Archived plans under `docs/done/` are left untouched.
4. Update `CHANGELOG.md` with an entry noting the removal of the dead 3.10
   compatibility shim, and `README.md` only if it still references the shim
   (it does not appear to).

## Non-goals

- No change to the supported Python version configuration: `requires-python`,
  tox `envlist`, CI matrices, and the README/CHANGELOG support statement belong
  to the separate "3.11-3.15 support" change. In particular, do **not** add
  3.15/3.15t to CI. Exception: `[tool.ty.environment] python-version` may be
  set to `"3.11"` on this branch to satisfy acceptance criterion 4
  (`just check`), because `ty` has no per-file `python-version` override and
  otherwise reports the unconditional `builtins` import as unresolved under
  3.10. This is a type-checker-only setting; the 3.11 support change supersedes
  it.
- No change to error messages in `zpcyclistfetch.py`, and no changes to other
  fetchers (`zpprimesfetch`, etc.) or the `validation.py` public API. The only
  error-semantics change is the correction of the task-group handler
  (requirement 1): it now actually surfaces the first `NetworkError`, which the
  pre-change guard never did.
- No regeneration of `uv.lock` to drop the `exceptiongroup` transitive
  dependency (it is marker-gated to `<3.11`; the lockfile follows the version
  support change).
- No edits to archived planning docs under `docs/done/`.

## Acceptance criteria

1. `grep -n "version_info\|exceptiongroup\|^import sys" src/zpdatafetch/zpcyclistfetch.py`
   returns no matches; the file imports `BaseExceptionGroup` from `builtins`
   unconditionally.
2. `grep -n "3.10 compat\|replace('Z'" src/shared/validation.py` returns no
   matches, and `test/test_shared/test_validation.py` passes, including
   `parse_datetime_to_epoch('2024-06-15T14:30:00Z') == 1718461800`.
3. Error propagation in `ZPCyclistFetch._fetch_parallel`: an `anyio` task group
   failure containing a `NetworkError` surfaces that `NetworkError` with the
   recorded message, and any other group is re-raised. This corrects the
   pre-change behavior, where the always-false guard meant the group was always
   re-raised. Existing cyclist async tests still pass.
4. `just test` and `just check` pass.
5. If `docs/planning/ty-exceptiongroup-unresolved-import.md` is present on the
   branch, it is removed or explicitly marked resolved; no tracked file still
   claims the `exceptiongroup` import needs a suppression.
6. `CHANGELOG.md` has an Unreleased entry for the cleanup.

## Assumptions

- **Version support is a separate change.** The issue explicitly says this
  cleanup was "found while updating the documentation for the 3.11-3.15
  support change". The maintainer has that change in progress and uncommitted;
  this branch still declares `requires-python = ">=3.10"`, tox `py310`, and CI
  `3.10` matrices. Those remain out of scope. Until the branch is rebased onto
  the 3.11 support change, its 3.10 CI job is expected to fail at import
  (the unconditional `builtins` import is not available on 3.10); this is
  accepted and documented, not fixed here.
- **`[tool.ty.environment] python-version = "3.11"`** is the one
  version-configuration setting this change touches, so `just check` passes
  under an interpreter that can resolve `builtins.BaseExceptionGroup`. See
  Non-goals.
- **`from builtins import BaseExceptionGroup`** is the form requested by the
  issue. It is equivalent to referencing the builtin directly; import it as
  written to match the issue.
- **Correction of the `except` handler** is treated as part of removing the
  shim, because the removed `else`/fallback branch is what the guard and
  comments protected. The guard was always false, so the intended behavior
  (surface the first `NetworkError`) was never reached; the change fixes that
  latent bug while leaving exception messages unchanged.
- **The ty suppression doc** (`ty-exceptiongroup-unresolved-import.md`) is
  untracked in this worktree and absent from the branch; requirement 3 is
  conditional so the worktree matches the issue without inventing a file.
- **Lockfile** is left to the version support change; `uv.lock` still lists
  `exceptiongroup` marker-gated to `<3.11`.

## Notes for implementation

- This is a dead-code removal, so there is no new user-visible behavior to test
  with production data. Keep existing regression tests. Add characterization
  tests for the corrected handler's two paths (a `NetworkError` in the group is
  surfaced; any other group is re-raised).
- Run `just check` locally — CI runs ruff with `continue-on-error`, so lint and
  `ty` failures will not fail CI.
