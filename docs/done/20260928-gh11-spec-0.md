# Spec: gh#11 — `ZwiftRideOns.rideon_ids()` returns wrong IDs

Issue: https://github.com/puckdoug/zpdatafetch/issues/11
Reported by: andrzejbluszcz

## Problem

`ZwiftRideOns.rideon_ids()` (src/zdatafetch/rideons.py:328) reads the top-level
`id` field of each rideon record. That `id` is the rideon record's own ID, not
the ID of the rider who gave the RideOn. The rider's ID lives in the nested
`profile.id` field of each record.

Consequence: `has_rideon_from(rider_id)` always returns `False`, because it
checks the caller's rider ID against rideon record IDs. The method is
therefore useless as documented.

Reporter's proposed fix:

```python
return [r.get("profile", {}).get("id") for r in self.rideons if r.get("profile")]
```

This matches the shape Zwift's API uses elsewhere: relation objects carry their
own `id` plus a nested profile dict (see the documented followers response,
where each entry has `id` + `followerProfile.id`).

## Required behavior

1. `rideon_ids()` returns the rider IDs (from each record's `profile.id`), not
   rideon record IDs. This is what its docstring already promises: "Return
   list of rider IDs who gave RideOns."
2. Records without a usable rider ID (missing `profile`, missing `id`, or
   non-int `id`) are skipped, so the return stays `list[int]` — no `None`
   entries. The reporter's snippet could leak `None` into the list; the
   implementation must not.
3. Malformed entries are skipped, never crash. If `profile` holds an unexpected
   non-dict type, ignore that record rather than raising.
4. `has_rideon_from(rider_id)` then works as documented: `True` iff that rider
   ID appears in `rideon_ids()`.
5. `self.rideons` and `self._fetched` keep the full parsed records unchanged —
   only the ID-extraction helpers change.

## Non-goals

- No change to `fetch()`, `fetch_multiple()`, `give_rideon()`, `_parse_response()`.
- No new public accessors beyond fixing the two existing methods.
- `ZwiftFollowers.follower_ids()` / `followee_ids()` have the same flat-`id`
  pattern and the documented API response nests profiles there too
  (`followerProfile` / `followeeProfile`). Suspected same bug, but out of
  scope here — file separately if confirmed by real data.
- No pagination support for the rideon endpoint (docs show
  `created_before`/`start`/`limit` params; current code takes the default 20).

## Acceptance criteria

1. `just test` and `just check` pass.
2. Regression tests in `test/test_zdatafetch/test_rideons.py` updated to use
   the real record shape (nested `profile.id`), covering:
   - `rideon_ids()` extracts `profile.id` values.
   - Records with missing `profile` or missing `profile.id` are skipped; no
     `None` in the result.
   - `has_rideon_from()` returns `True`/`False` correctly on real-shaped data.
   - Existing flat-shape test data (`{'id': ..., 'firstName': ...}`) is
     replaced — it encodes the wrong assumption.
3. Live validation against the real Zwift API (not just mocks): fetch RideOns
   for one activity via `just test-live` or an equivalent live check and
   confirm `rideon_ids()` values are rider IDs that `has_rideon_from()` can
   match. This also confirms the assumed `profile.id` shape against production
   data; if the real shape differs, stop and re-spec.
4. CHANGELOG.md and README.md updated (semantic change to `rideon_ids()`
   return values, now-correct `has_rideon_from()`).
