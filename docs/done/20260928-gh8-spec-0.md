# Spec: gh#8 — Followers/followees limited to 200

Issue: https://github.com/puckdoug/zpdatafetch/issues/8
Reported by: andrzejbluszcz

## Problem

Zwift's `/api/profiles/{riderId}/followers` and `/followees` endpoints are
paginated: each request returns at most 200 entries (page 1 by default).
`ZwiftFollowers.fetch()` and `fetch_multiple()` (src/zdatafetch/followers.py)
make a single unparameterized GET per endpoint, so any rider with more than
200 followers or followees silently gets a truncated list. Downstream helpers
(`follower_count()`, `followee_count()`, `follower_ids()`, `followee_ids()`,
`mutual_followers()`) then report wrong numbers with no error raised.

The reporter verified with real requests that passing `start` and `limit`
query parameters paginates correctly, and that looping until a page is empty
or shorter than `limit` collects the complete list:

```python
f"https://us-or-rly101.zwift.com/api/profiles/{my_id}/followers?start={start}&limit={limit}"
```

## Required behavior

1. `fetch()` and `fetch_multiple()` paginate both endpoints with
   `start`/`limit` query parameters. Page size is an explicit `limit=200`.
2. Offsets step by page size: `start = 0, 200, 400, ...`. Pages are
   accumulated in request order.
3. Pagination stops when a page is empty OR shorter than `limit`. Both stop
   conditions are needed: a rider with exactly N×200 entries yields full
   pages followed by an empty one; a shorter final page also terminates.
4. The merged full list is stored in `self.followers` / `self.followees` and
   flows into `_fetched` / `_raw` unchanged in shape — no new keys, no page
   boundaries visible to callers.
5. Both followers and followees paginate identically. The reporter verified
   followers empirically; followees use the same endpoint family and are
   assumed to behave the same (verified in live validation).
6. Error handling keeps existing semantics per failed page:
   - `fetch()`: non-200 followers page → `NetworkError` (404 keeps the
     "Rider not found" message). Failed followees page → log warning, stop
     paginating followees, keep pages collected so far (empty list if the
     first page fails, matching current behavior).
   - `fetch_multiple()`: failed followers page → skip that rider (existing);
     failed followees page → log warning, keep collected-so-far pages.
7. Loop guard: cap pagination at 500 pages (100k records) per endpoint. If
   the cap is hit, log a warning and return the partial data rather than
   looping forever on a misbehaving server.
8. Implement the page loop once in a private helper (e.g.
   `_fetch_paginated(client, url, headers, context) -> list[dict]`), called
   from both `fetch()` and `fetch_multiple()`. No duplication.

## Non-goals

- No CLI changes (`zdata` output format unchanged).
- No async variant — the zdatafetch package has no `afetch()` methods.
- No pagination for other endpoints (rideons, activities, profiles).
- No change to public signatures of `fetch()` / `fetch_multiple()` or any
  helper methods.
- No config option for page size.

## Acceptance criteria

1. `just test` and `just check` pass.
2. Unit tests in `test/test_zdatafetch/test_followers.py` mock
   `httpx2.Client` (pattern used by `test/test_zdatafetch/test_auth.py`) and
   cover:
   - Single page shorter than `limit` → exactly one request.
   - Multiple pages merged in order (e.g. 250 followers → 2 requests,
     correct concatenation).
   - Exactly N×`limit` entries (e.g. 400) → terminates via the empty-page
     stop condition, no infinite loop.
   - Query parameters actually sent: `start` and `limit=200` present and
     stepping correctly.
   - Mid-pagination failure for followers → `NetworkError` in `fetch()`.
   - Mid-pagination failure for followees → warning logged, partial data
     kept.
   - Loop-guard cap → warning logged, partial data returned.
   - `fetch_multiple()` path paginates too.
3. Test page payloads use the real API record shape (entry dicts with `id`
   plus `followerProfile`/`followeeProfile`, per the gh-11 verified shape) —
   no made-up substitutes.
4. Regression check against production: a rider with >200 followers returns
   a complete list (`follower_count()` > 200). Verified live via
   `just test-live` during implementation, with the reporter's account
   pattern as the real-data check.
5. `CHANGELOG.md` and `README.md` updated (document that followers/followees
   fetch all pages).
