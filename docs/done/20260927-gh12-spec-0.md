# GH-12 Spec — round 3: rename ZRCategoriesEntry to ZRvELOCategory

Date: 2026-09-27
Stage: review
Branch: `pipeline/gh-12`
Issue: New endpoint for vELO2 category ranges

## History

- Round 1 (done): added `zrdata categories`, `ZRCategories` /
  `ZRCategoriesEntry` dataclasses, `ZRCategoriesFetch`, CLI subcommand,
  tests, docs.
- Round 2 (done): full repr instead of count-only; container protocol
  (`__iter__`, name/int/slice `__getitem__`, `__contains__`, `__len__`).
- Round 3 (this spec): maintainer feedback —
  "ZRCategoriesEntry should be renamed to ZRvELOCategory - The ZwiftRacing
  category system is vELO".

## Problem

`ZRCategoriesEntry` does not follow the project's naming convention of
naming zr dataclasses after the actual ZwiftRacing data system. The
category system is vELO, so the per-category dataclass should be
`ZRvELOCategory`.

## Required behavior

Pure rename of the dataclass `ZRCategoriesEntry` → `ZRvELOCategory`.
No behavior change. Specifically:

1. `src/zrdatafetch/zrcategories.py`: rename the class and every
   type-hint/docstring reference (13 occurrences). `from_dict`,
   `asdict`, `excluded`, `extras`, and all fields keep their names.
2. `src/zrdatafetch/zrcategories.py`: in `ZRCategories`, update the
   `categories: list[...]` annotation and all return/iterator types
   (`__getitem__` overloads, `__iter__`) to `ZRvELOCategory`.
3. `src/zrdatafetch/__init__.py`: import and `__all__` export
   `ZRvELOCategory`; remove `ZRCategoriesEntry`.
4. `test/test_zrdatafetch/test_zrcategories.py`: update imports,
   constructions, `from_dict` calls, the repr assertion
   (`'ZRvELOCategory(' in r`), and test class names
   (e.g. `TestZRCategoriesEntryParsing` → `TestZRvELOCategoryParsing`).
5. Docs: README.md repr example, CHANGELOG.md Unreleased entry, and
   `docs/DATA_DICTIONARY.md` ZRCategories lineage section all reference
   `ZRvELOCategory`.
6. `ZRCategories`, `ZRCategoriesFetch`, the module file
   `zrcategories.py`, the CLI subcommand, and the fixture
   `test/fixtures/zr_categories.json` keep their current names.
7. No deprecation alias: the feature is unreleased, so
   `ZRCategoriesEntry` disappears entirely.

## Non-goals

- No rename of `ZRCategories` or `ZRCategoriesFetch` (only the entry
  dataclass was named in the feedback).
- No module/file rename, no CLI flag changes, no API/parse changes.
- No backwards-compatibility alias or deprecation shim.
- No changes to other dataclass families.

## Acceptance criteria

1. `from zrdatafetch import ZRvELOCategory` works;
   `from zrdatafetch import ZRCategoriesEntry` fails.
2. `ZRCategories.categories` is `list[ZRvELOCategory]`; parsing the
   verbatim fixture (`test/fixtures/zr_categories.json`) still yields 10
   entries with correct values (Diamond `min=920, max=None`; Silver
   `min=420, max=479`; Copper `min=0, max=359`).
3. Round-2 container protocol unchanged: iteration in API order,
   `categories['Silver']`, `categories[0]`, slices, `'Silver' in
   categories`, `len(categories) == 10` — all still return
   `ZRvELOCategory` instances.
4. `repr` output contains `ZRvELOCategory(number=1, name='Diamond',
   min=920, max=None)` style entries.
5. `grep -r ZRCategoriesEntry src test README.md CHANGELOG.md
   docs/DATA_DICTIONARY.md` returns no matches (historical planning
   files in docs/planning/ are out of scope).
6. `just test` and `just check` pass.
