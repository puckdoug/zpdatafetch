## Design decisions

1. **Flat `velo_*` naming.** Follow the established convention used by the
   existing `velo_race`, `velo_factors.*` fields. No nested sub-dataclass
   (spec non-goal). Field order after the existing velo fields: six skill
   floats, then category int, then category str.
2. **`velo` stays in `known_fields`.** The sub-object is now fully typed, so
   it must not leak into `_extra`. No change to the classification loop.
3. **Fixture, not a new file.** Add the issue's exact `skill` and `category`
   blocks to the existing `zr_rider_550564.json`. This keeps one fixture,
   leaves every existing assertion untouched, and puts the exact production
   values that triggered the bug into the regression test. The issue
   supplies only the `velo` block, so grafting it onto the real rider wrapper
   is the closest faithful reproduction.
4. **Malformed values fall back to defaults.** Reuse `safe_float` /
   `safe_int` / `safe_str`; `None` / non-numeric input yields `0.0` / `0` /
   `''` and never raises (spec required behavior 3).
5. **No other change.** `asdict()`, `extras()`, `excluded()`, the fetch
   layer, CLI, and `--raw` are untouched.
6. **`zrriderfetch.py` rebuild path out of scope.** The `zwift_id == 0`
   manual rebuild already drops every field added since 2.1.0; the new
   fields inherit that latent bug. The spec logs it as a separate follow-up
   (replace with `dataclasses.replace`). Do not fix here.
