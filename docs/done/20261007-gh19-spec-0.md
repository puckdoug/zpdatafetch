# GH #19 spec — Retry and configurable timeout for ZwiftPower login

Date: 2026-10-07
Issue: https://github.com/puckdoug/zpdatafetch/issues/19
Branch: `pipeline/gh-19`

## Problem

`AsyncZP.login()` performs the credential POST to the Zwift SSO endpoint
directly through `self._client.post()` (`src/zpdatafetch/async_zp.py:184`).
It is the only request in the class that bypasses
`shared.http_client.fetch_with_retry_async`, so a transient
`httpcore2.ReadTimeout` is converted straight into `NetworkError` with no
retry.

`AsyncZP._create_client()` (`async_zp.py:226`) constructs
`httpx2.AsyncClient(follow_redirects=True, verify=True)` with no `timeout`,
so httpx2's default 5-second timeout applies to every request, including the
SSO POST. A slow SSO response therefore fails login on the first attempt.

The sync `ZP.login()` / `ZP._create_client()` (`src/zpdatafetch/zp.py`) have
the identical defect: the POST at `zp.py:181` bypasses
`fetch_with_retry_sync`, and the client uses the httpx2 default timeout.

## Required behavior

### 1. Retry the login POST

- Both `AsyncZP.login()` and `ZP.login()` submit credentials through the
  shared retry helper (`fetch_with_retry_async` / `fetch_with_retry_sync`)
  instead of calling `client.post()` directly.
- The helper is called with method `POST`, the extracted form action URL,
  and the existing `data={'username': ..., 'password': ...}` payload (plus
  `cookies` where already passed). Do not log the payload, the data dict, or
  the credential-bearing URL; the existing "SECURITY" comment stays.
- Transient errors (`httpx2.ConnectError`, `httpx2.TimeoutException`,
  5xx-after-retries) are retried using the helper's default retry count
  (3) and backoff (1.0 s). 4xx responses are not retried, matching the
  helper's existing policy.
- The existing user-facing error message is preserved. The helper raises
  `NetworkError('Failed after N attempts: ...')` on exhaustion; `login()`
  catches that and re-raises `NetworkError` built with
  `format_network_error('authenticate with Zwiftpower', <url>, e)` so the
  message keeps the `Failed to authenticate with Zwiftpower:` shape and
  endpoint line shown in the issue traceback. `AuthenticationError` for
  wrong credentials (redirect back to `ucp.php?mode=login`) is unchanged.
- The post-response login-success check (`ucp.php`/`mode=login` redirect
  detection) and the `Authenticator`/`HTTPStatusError` handling remain
  unchanged.

### 2. Configurable client timeout

- `AsyncZP.__init__` and `ZP.__init__` gain a keyword argument
  `timeout: float = 30.0`.
- The value is stored on the instance and passed to the httpx2 client in
  both `_create_client()` and the shared-client construction path
  (`AsyncZP.__init__` / `ZP._shared_client`), i.e.
  `httpx2.AsyncClient(follow_redirects=True, verify=True, timeout=self.timeout)`
  (sync equivalent for `ZP`).
- The default becomes 30.0 seconds, replacing httpx2's implicit 5 seconds.
- Existing call sites (`AsyncZP()`, `AsyncZP(skip_credential_check=True)`,
  `shared_client=True`, CLI) keep working unchanged because the argument is
  optional and last.

## Non-goals

- No new CLI flag or config-file key to set the timeout; programmatic
  configuration only (issue only requires that a user *can* configure it).
- No change to retry counts, backoff, or adding per-request timeouts.
- No change to `_login_url`, credential loading, `clear_credentials`, or the
  login-form parsing/`AuthenticationError` paths.
- No change to `fetch_json` / `fetch_page` behavior.
- No change to other packages (`zrdatafetch`, `zdatafetch`, `zsdatafetch`);
  they already pass `timeout=30.0`.
- No retry of non-idempotent-looking authenticated *data* POSTs; only the
  SSO login POST is in scope.

## Tests

Regression tests use `httpx2.MockTransport`; no live calls.

1. `AsyncZP.login()` retries when the POST raises `httpx2.ReadTimeout` (or
   `ConnectError`) and succeeds on a later attempt. Assert the client saw
   more than one POST and `login_response` is set. Same for sync `ZP` with
   a sync `httpx2.MockTransport`.
2. `login()` still raises `NetworkError` when every attempt fails, and the
   message contains `Failed to authenticate with Zwiftpower` and the SSO
   endpoint.
3. Wrong-credential redirect still raises `AuthenticationError` (existing
   test unchanged).
4. `AsyncZP(timeout=<x>)._create_client()` / `init_client()` creates a
   client whose timeout equals `<x>`; same for `ZP`. Default instance uses
   30.0.
5. Existing `test_async_zp.py` / `test_zp.py` login, missing-form, and
   network-error tests continue to pass; adjust only if the retry wrapper
   changes their expected exception (keep them asserting `NetworkError`).

## Acceptance criteria

- [x] `AsyncZP.login()` retries transient network errors on the SSO POST and
      no longer raises `NetworkError` on the first transient failure.
- [x] Returning `NetworkError` from `AsyncZP.login()` after exhausted retries
      keeps the `Failed to authenticate with Zwiftpower` message and endpoint.
- [x] `AsyncZP(timeout=...)` configures the client timeout; default is 30.0.
- [x] The equivalent sync `ZP.login()` / `ZP(timeout=...)` changes are made
      so sync and async behavior stay in parity.
- [x] New regression tests fail before the change and pass after.
- [x] `just test` passes.
- [x] `just check` passes.
- [x] `CHANGELOG.md` and `README.md` updated.

## Assumptions

- **Sync `ZP` fixed too.** The issue names `AsyncZP` only, but `ZP.login()`
  has byte-for-byte the same defect and the project convention is that every
  data class supports both sync and async. Fixing both keeps parity; the
  change is mechanical and low-risk.
- **Default timeout 30.0 s.** The library's other clients already use
  `timeout=30.0` (`zrdatafetch`, `zdatafetch`, `zsdatafetch`). Using 30.0
  for `zpdatafetch` is the project-consistent fix for the SSO slowness and
  directly satisfies "no `NetworkError` on first attempt due to transient
  SSO response delays."
- **No CLI/config timeout.** The issue asks only that a user *can* configure
  it; an `__init__` argument satisfies that. A CLI flag is a separate
  product decision, so it is out of scope.
- **Retry the SSO POST.** Retrying the authenticate POST is acceptable for
  transient connection/timeout errors and 5xx; the helper's 4xx policy still
  prevents retrying bad credentials.
